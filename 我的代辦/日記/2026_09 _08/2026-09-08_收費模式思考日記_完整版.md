# 日記 · 2026年9月8日 —— 開源收費模式研究：從 screenshottocode.com 到湛箴四面板

## 起因

今天在看 [Screenshot to Code](https://screenshottocode.com/) 這個工具，順手查了它背後的 GitHub 倉庫 [abi/screenshot-to-code](https://github.com/abi/screenshot-to-code)，發現它的商業邏輯跟我一直在設計的「湛箴(Zhanzhen)」四面板服務(Docs + 試算表 + 文件管理 + AI 智能體協作整合)幾乎是同一套打法。把今天查到的資料完整記一下，順便理清楚這到底叫什麼收費模式，以及該怎麼套用到我自己的產品上。

## 一、screenshottocode.com 的具體數據

先把查到的硬事實記下來，不是空泛印象:

- **倉庫**：[github.com/abi/screenshot-to-code](https://github.com/abi/screenshot-to-code)，作者 Abi Raja。
- **授權**：倉庫 Resources 區塊明確標示 **MIT license**，README 也沒有任何 Enterprise/付費分支的字樣——代碼是完整的一份，沒有閹割。
- **規模**：78.2k stars、9.5k forks、431 watchers、26 位貢獻者，1,455 次提交，最近一次提交是 2026年7月30日，項目仍在活躍維護。
- **技術棧**：後端 Python(FastAPI + Poetry)佔 53.6%，前端 TypeScript(React/Vite + pnpm)佔 45.3%。
- **背後模型**：Gemini 3 Flash/3.1 Pro、GPT-5.5/5.4 Mini、Claude Opus 4.6/4.8，圖像生成用 Replicate 的 z-image-turbo。README 裡明確寫「至少需要一個模型商的 Key(OpenAI/Anthropic/Gemini 三選一)，強烈建議加 Replicate」。
- **自架方式**：`docker-compose up -d --build` 一行指令，或分別跑 backend(`poetry run uvicorn`)和 frontend(`pnpm dev`)，完全對得上我自己熟悉的 VPS/Docker 部署習慣。
- **收入來源**：倉庫有 `FUNDING.yml`，開了 GitHub Sponsors 讓人贊助 Abi Raja 個人；同時官網託管版本(screenshottocode.com)本身就是主要商業出口。

結論：這不是「閹割版開源」，是「**完整開源 + 官方託管服務**」的純自架/託管二選一模式。

## 二、這到底是什麼收費模式(理清概念)

查了幾篇業界文章後，把概念層級理順:

**COSS(Commercial Open Source Software，商業化開源軟體)是總稱**，底下常見三個變體，我容易搞混，列表對照一下:

| 模式 | 代碼開放程度 | 收費點 | 代表案例 |
|---|---|---|---|
| Open Core(開源核心) | 社群版功能閹割，好功能鎖進企業版 | 賣「功能」，走銷售/企業合約 | GitLab CE/EE、Strapi Enterprise Edition |
| 自架免費 + 託管付費(Self-hosted vs. Managed Cloud) | 代碼完全一致，不閹割任何功能 | 賣「省事」+「代管算力/API 成本」 | n8n、Supabase、Plausible、**screenshot-to-code** |
| 純 SaaS | 代碼不開放 | 賣訂閱/使用量 | 絕大多數傳統 SaaS |

參考文章：[Strapi：Open Core vs SaaS 該怎麼選](https://strapi.io/blog/the-business-model-dilemma-of-open-source-startup)、[Snowplow：COSS 相對 SaaS 的 5 個優勢](https://snowplow.io/blog/coss-vs-saas)、[TechTarget：什麼是 Open Core 模式](https://www.techtarget.com/it-infrastructure/definition/open-core-model-open-core-software)、[維基百科：開源軟體商業模式列表](https://en.wikipedia.org/wiki/Business_models_for_open-source_software)。

screenshottocode.com 和我要走的湛箴路線，明確屬於**第二種**——不是 Open Core。這點很重要，之前我可能把兩者混著想了。

### Strapi 的真實踩坑經驗，值得借鏡

Strapi(58k stars 的開源 CMS)先走了 Open Core，後來又補了 Strapi Cloud(託管版)，他們公開分享的經驗很值得記下來:

**Open Core 階段的收穫與坑**

- 好處：不用管基礎設施，企業客戶願意為額外功能付費，幫他們拿到了 B 輪融資。
- 坑：免費版和付費版的邊界容易讓用戶困惑；因為軟體跑在客戶自己的伺服器上，**用量根本沒法追蹤**，這讓續約、擴張都變得很難算。

**轉向 Strapi Cloud(託管版)之後的收穫與坑**

- 收穫：用戶反饋一直是「我愛 Strapi，但我不想管伺服器」——這句話幾乎跟我對湛箴用戶的預期一樣。轉向託管版後，**縮短了用戶拿到價值的時間**，而且是「賣算力」而不只是「賣功能」，更適合自助式(self-serve)增長。
- 坑：需要新的團隊技能(SRE、PLG 增長、客戶成功)，架構要改成多租戶(multi-tenant)，這是「第二個產品」要重新建。

原文連結：[Strapi 部落格：開源創業公司的商業模式困境](https://strapi.io/blog/the-business-model-dilemma-of-open-source-startup)。

Strapi 的結論一句話很戳中我：「公司更習慣為託管軟體付錢，而不是為功能付錢——如果客戶要自己用自架版，他們反正也要自己買伺服器，所以更可能直接付錢讓你託管。」這句話幾乎是在給湛箴的定價策略打廣告。

## 三、COSS 模式對用戶的五個具體好處(用戶視角，也是我要在落地頁上打的賣點)

引自 Snowplow 的分析，翻譯成我自己的話:

- 部署選項多：用戶可以先白嫖自架版試用，覺得值了再升級託管付費版，決策風險低。
- 靈活可定制：不像純 SaaS 那樣被框死工作流，開源代碼可以自己改。
- 無廠商鎖定：真出問題了隨時能搬走，不怕被綁死。
- 社群效應：用的人多，代碼更經過千錘百煉，bug 少。
- 安全可審計：代碼公開，任何人都能審查，比黑箱 SaaS 更讓技術用戶放心。

參考：[Snowplow：COSS 相對 SaaS 的 5 個優勢](https://snowplow.io/blog/coss-vs-saas)。

這五點剛好也是我一直堅持「必須基於真開源、可自架方案」的底層邏輯——原來這套邏輯業界早就總結好了，不是我瞎想的。

## 四、對湛箴四面板的具體套用

湛箴的四面板(Docs + 試算表 + 文件管理 + AI 智能體協作整合)，介面追求 Proton Docs + Proton Sheets 那種極簡乾淨感，現在收費策略可以照著 screenshottocode.com / n8n / Supabase 這套「自架免費 + 託管付費」再細化:

**兩條收費腿(維持原方案，但補充理由)**

- 按量計費：用戶自己接 API Key(對應 screenshot-to-code 的「至少一個模型 Key」邏輯)完全免費；用我託管的路由則抽約 20% 利潤——這就是「代跑算力」的錢，跟 screenshot-to-code 每次生成要真金白銀呼叫 Gemini/GPT/Claude 是同一個成本結構。
- 訂閱制：全球化低價訂閱(約 1.5 USDT/月，Stripe 支付)，賣的是「省事」——不用自己申請多個 Key、不用管 Docker、不用管伺服器擴容，這正是 Strapi 用戶那句「我愛用但不想管伺服器」要解決的痛點。

**還沒想清楚、需要下一步решить的問題**

- 引導體驗：怎麼設計首次使用流程，讓新手覺得「託管版理所當然要付錢」，而不是「反正開源我幹嘛付錢」？screenshot-to-code 的做法是README第一句就寫「試用最快方式是用官方託管版」，把自架選項放在第二位——這個「預設路徑」的心理暗示值得抄。
- 用量追蹤：Strapi 踩過的坑是自架版用戶的用量沒法追蹤，導致續約很難算。湛箴如果也提供自架版，要不要在自架版里做一個「可選的匿名用量回報」機制，方便未來做增長分析？
- 多租戶架構：如果做託管版，現在的架構要不要提前按多租戶設計，避免將來像 Strapi 一樣要重構?
- 定價驗證：1.5 USDT/月這個數字目前是拍腦袋，需要找同類產品(n8n Cloud、Supabase 定價頁)做基準比對，看是不是定得太低或太高。
